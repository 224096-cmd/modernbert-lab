このシステムは何か

「公開情報を集め、長文をそのまま読める日本語 ModernBERT で、どれを信じてよいか・何が分かっていないか・どう整理できるかを機械が根拠つきで示す」ためのシステム。生成 LLM は使わない。集める部分は無料の検索エンジンと公開 API だけ、判定する部分は 22〜68 MB の小さなエンコーダだけで、すべてあなたの端末のブラウザの中で動く。サーバも API キーも不要で、入力も結果もどこにも送られない。

トピック／URL→Dorks で検索エンジン巡回→本文抽出→信頼性採点→コーパス（端末内）→検証・ギャップ・構造化

研究の核（何を明らかにしたいか）

  1. 長文一括処理の優位性：文章を 512 トークンに切り刻んで処理する従来手法より、8,192 トークンを分割せず読む ModernBERT のほうが、矛盾検知・関連度判定で精度が高く、LLM より低コスト・高速か。「長文 vs 分割」タブで同じ文書・同じ問いを両方式で処理し、判定と時間を記録する
  2. 不足情報・反対視点の自律的発見：12 種類の問い（誰が・いつ・根拠・反対意見…）が集めた記事で答えられているかを判定し、答えのない問いに検索式を提案する。反対意見・矛盾する記述を列挙する。人が「偏った情報収集」に気づく助けになるか
  3. 長文から構造化データへの直接変換：記事群を軸（メリット／デメリット／費用／時期／根拠）ごとの比較表にし、根拠つきで要約する。人にとって見やすい形に、生成なしで変換できるか

独自モデルへの道筋（この版では学習はまだ行わない）

まず既存の 7 モデル（日本語 ModernBERT 系 4 つ、海外の多言語モデル 3 つ）を同じタスクで比較する。その結果と、このサイトで集めた実データ（記事・段落・判定）を使って、次の段階で土台モデル（modernbert-ja-30m/70m/130m）を検証・構造化タスクに特化して微調整する。土台の候補は「モデル」タブに整理してある。ModernBART（生成型）の日本語公開モデルは未確認のため、要約は当面「抽出型」で行う。

収集の仕組み

  • Dorks：トピックから "…"、site:go.jp OR site:lg.jp OR site:ac.jp、filetype:pdf、ファクトチェック媒体、否定語（デマ／訂正／事実無根）などの検索式を自動生成。Google 固有の after: は使わず、DuckDuckGo・Bing・Yahoo! JAPAN が解釈する演算子だけ
  • エンジン（ブラウザ）：DuckDuckGo・Bing・Yahoo! JAPAN（r.jina.ai リーダー経由）、Google ニュース RSS・はてなブックマーク（rss2json 経由）、Wikipedia（API 直接）。PC 版（python -m mbo）ではさらに Mojeek、Bluesky、Mastodon、Reddit、GDELT、Qiita、GitHub、NHK RSS、ウィキニュース、Crossref、OpenAlex、Wayback CDX が使える
  • マナー：ブラウザ相当の UA、同一ホストへは 1.2 秒以上あける、robots.txt を尊重（禁止ならリーダー経由の要約だけ）、本文は判定に使うだけで公開データには 200 字以内の根拠段落しか残さない
  • 本文抽出：ブラウザでは r.jina.ai リーダー（無料・鍵なし）の Markdown を平文化。PC 版は trafilatura（本文・著者・日付・媒体名・JSON-LD）
  • ドメイン調査：Google DNS over HTTPS、RDAP（gTLD）／JPRS whois（.jp）、crt.sh（証明書ログ→サブドメイン）、HackerTarget（ホスト・GeoIP）、archive.org（最古・最新スナップショット→年齢）、urlscan.io（公開スキャン）、Wikipedia exturlusage（出典に使われた回数）、セキュリティヘッダ

判定の仕組み（式は「仕組み」タブ、値は params.json）

  1. 出所：ドメイン種別（公的／教育／報道／学術／百科／団体／企業／ブログ／SNS）に基礎点。HTTPS、Wayback で見た年齢、Wikipedia 出典回数、著者・日付で加減点
  2. 内容：本文の長さ、具体性（数値・日付・引用・固有名詞の密度）、文体（Ruri 埋め込みとラベル文「煽り／報告／意見／宣伝」の類似 → softmax）
  3. 裏取り：各ページの要旨（冒頭の 1 文）を「検索クエリ」として埋め込み、他ドメインの段落（「検索文書」）の上位 k を取り、JNLI モデルで含意／中立／矛盾を判定。含意は出所重み×確率で加点、高類似の中立は部分点、矛盾は減点。飽和関数 1−e−S/2 で 0〜1 に
  4. 時間：日付の新しさ（半減期 30 日）
  5. 主張検証：主張を埋め込み → 段落上位 k → NLI → 支持 Σw·P(含意)、反証 Σw·P(矛盾) → 支持／否定／食い違い／根拠不足
  6. 話題クラスタ：見出し＋抜粋の「トピック」埋め込みで cos ≥ 0.975 をつなぐ単純な連結法。何ドメインが同じ話を伝えているか、最初に出たのはどこかを出す

Ruri の cos は無関係な文でも 0.85 前後と高い（異方性）ので、しきい値は 0.90〜0.975 に置いてある。ONNX int8 化で JNLI 正解率は fp32 より 2〜3 ポイント下がる（分類ヘッドは量子化しない）。

限界と注意

  • 信頼性スコアは「他の情報源との整合と出所の性質」を数値化したもので、真偽そのものではない。A でも誤り、D でも正しいことはある。根拠段落を必ず読む
  • JNLI は画像説明文で作られたデータなので、ニュース文への転移は完全ではない（だから自作ラベルでの微調整が研究の中心になる）
  • 検索エンジンの HTML は予告なく変わる。壊れたら engines.py のパーサを直す。r.jina.ai は無料枠 20 回/分
  • 人物検索・アカウント特定・ポートスキャン・ログインが必要な取得は実装しない（以後も）
